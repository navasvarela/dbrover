SQL, NoSQL and cloud databases in one native app

DbRover is a native desktop database tool written in Rust: it opens in a moment and stays quick with millions of rows. Safety levels guard production, reports gather several databases into one file, and AI assistants reach your databases over MCP only as far as you allow. Free, open source, and no account to make.

Native and fast

Rust and egui, with no browser engine or JVM inside. It opens in about a third of a second on a recent Mac, and results stream in as you scroll, so even a huge table shows at once.

Features

AI assistants through MCP

Let an assistant in, as far as you allow

DbRover includes an MCP server. Allow a project, copy its configuration into Claude Desktop, Claude Code, Cursor or another client, and the assistant can list, describe, explain and query that project's data sources, with the DbRover window closed.

  • Off until you allow a project, and read-only until you allow more.
  • Read, write, schema and admin permissions per project, a row limit, a statement timeout, and the schemas it may see.
  • Checked in layers: DbRover reads each statement first, reads run in the database's own read-only mode, and the database's grants apply through an MCP login of its own.
  • Every statement in the history, marked with the assistant's name.

Reports

Several databases, one file, every month

A report is a query you run again and again with new values, and the files it writes each time. It reads one data source or several, combines them in DuckDB SQL or PRQL, and writes CSV, Excel and Parquet files, with charts of them as SVG or PNG. It runs in a process of its own, within limits you can see, from its tab or from dbrover report run in a terminal, cron or CI.

  • Profile draws a run on a timeline and names its bottleneck: the step that held the run longest, and what it waited on.
  • Each step's pace while it runs, and every run kept, to compare with the next, with a mark on a step slower than usual.
  • Hints that say what to try, such as filtering in the source's query, each with an id a report can silence.
  • Explain plans a report before it runs: each source's plan, what a warehouse would scan, and the combine step's plan.
  • Larger than memory: DuckDB works on disk, within the space a run may use, and the computer stays awake through a long run.

Staying safe

Careful where it matters

Each data source has a safety level. Normal asks before an UPDATE or DELETE without WHERE. Careful asks before every change, naming the data source, and opens consoles in manual commit. Read-only refuses changes on every database, and PostgreSQL, MySQL, MariaDB, SQLite, DuckDB and ClickHouse refuse them in their own read-only modes too.

  • A colour per data source, on its tree row, its console tabs and a band across the console.
  • Manual-commit transactions, and a question before closing one that's open.
  • A history of every statement, from consoles, the grid, dialogs, imports and assistants, with the grid's values before and after.
  • Passwords stay in the system keychain, and out of the history.

Writing SQL

SQL that knows your schema

Completion suggests tables after FROM and columns after an alias, and follows CTEs and subqueries; cid finds customer_id. Problems are marked as you type: = NULL, an UPDATE without WHERE, an unknown column, and what the database itself says.

  • Run the statement at the cursor or the whole script, explain it, cancel it.
  • Format a statement or a whole console, leaving strings and comments alone.
  • Open, save and drop in .sql files; edits made elsewhere are picked up.
  • :name parameters, asked for as you run; find and replace with regular expressions.
Query consoles in the manual

Charts

A chart from any result

Chart, beside Grid, draws the rows as bars, lines or a scatter, and follows the grid as you sort, filter and load more. Nothing runs again.

  • A column to split the rows into series, and stacked bars, with no pivot in the query.
  • Write the chart above its query, in a comment, and the query opens as that chart on any machine, reviewed with it in a pull request.
  • Export as SVG or PNG; reports draw charts of their files, and an assistant can ask for one over MCP.
Charts in the manual

Query plans

See why a query is slow

Explain draws the plan as a tree of steps and tints the costliest. Explain analyse runs the statement and shows, beside each estimate, the rows each step really returned, how many times it ran and how long it took.

  • On PostgreSQL, MySQL, MariaDB and SQL Server.
  • Estimates that were ten times off are flagged: the usual reason the database picked a slow plan.
  • Hover over a step for its join condition, filter, sort key or index.
  • Copy the plan as text, or as the JSON or XML the database returned.
Reading query plans in the manual

Beyond SQL

Keys, documents and indices too

Redis, Valkey and Dragonfly, MongoDB, Elasticsearch and OpenSearch, Cassandra and ScyllaDB, and DynamoDB each get a console in their own language, with completion, and an explorer that knows their shape.

  • Redis keys grouped by their separator, read with SCAN so even millions never stall the server.
  • MongoDB's shell commands, read by DbRover before they're sent, with documents as columns, a tree or JSON.
  • Elasticsearch and OpenSearch requests as Kibana's Dev Tools write them, with every hit paged in as you scroll.
  • Cassandra and ScyllaDB in CQL, checked by the server as you type, with maps and sets as a tree and rows edited by their primary key.
  • DynamoDB's PartiQL, signed in with your AWS profile, and a guard that asks before a statement reads a whole table.
Each database's console in the manual

Cloud data

Warehouses and data lakes, with the bill in view

Athena, BigQuery and Trino are data sources like any other, and a DuckDB data source reads Parquet, CSV and JSON files and Iceberg and Delta tables in Amazon S3, Google Cloud Storage or Azure Blob Storage, joined with its own tables.

  • A cost guard: BigQuery's dry run says what a query would scan before it runs, and asks above your limit; Athena stops a query that passes it.
  • DynamoDB asks before a statement reads a whole table.
  • Progress as a statement runs, with the rows and bytes read so far.
  • Buckets in the explorer beside the database, signed in with the account already on your machine.
Cloud sign-in and costs in the manual

The results grid

A grid that edits, and asks the database

Rows arrive 500 at a time. Sort and filter the rows loaded, or tick In the database to have it sort and filter every row.

  • Edit cells, add and delete rows, then submit them together or revert.
  • Follow a foreign key to the row it points at, or list the rows pointing back.
  • Export to CSV, Excel, Parquet, JSON, Markdown, SQL and more, from the grid, a table, or a query run straight to a file.
  • Import a CSV file into a table, with a preview and warnings first.
Exporting and copying rows in the manual

Changing the schema

Change the schema without writing the DDL

Dialogs for tables, indexes, views and materialized views, schemas, and PostgreSQL users and roles write the SQL and show it. Nothing runs until you press Execute, or open it in a console instead.

  • Modify table renames, adds and changes columns, and says what each database can change in place; SQLite's table is rebuilt for the rest.
  • A change of several statements runs in one transaction where the database can, and warns first where it can't.
  • Copy any table's DDL.
Creating and changing tables in the manual

Diagrams and schema compare

See a schema whole, and what changed

A diagram draws the tables you pick, or a whole schema, with their columns and the foreign keys between them, laid out for you and saved as you arrange it.

  • Diagrams on PostgreSQL, MySQL, MariaDB, SQLite, SQL Server and DuckDB, exported as SVG or PNG.
  • Compare schema sets two PostgreSQL schemas side by side and writes the script that turns one into the other, for you to read and run.
  • Save a schema as a snapshot, a text file to keep in Git and compare with later, or check it from dbrover schema compare in CI.
ER diagrams in the manual

Connecting anywhere

Reach the database where it runs

On your laptop, on a server behind SSH, or in the cloud: DbRover connects to the database where it already runs, and signs in the way your team already does.

  • SSH tunnels on every server database, through your agent, a key file or a password, with host keys checked against known_hosts.
  • TLS up to verify-full, with your own CA file and no OpenSSL to install.
  • A password from the keychain or from a command such as your password manager's, and ${VARIABLE} placeholders in connection settings.
  • AWS IAM, Google Cloud and Microsoft Entra ID sign-in, from the sign-in already on your machine, with no cloud secret kept.
  • Projects to group data sources, and a file to move them to another machine, without their passwords.

Making it yours

Bend it with plain files

DbRover keeps its settings in files you can read and edit, next to each other.

  • keymap.toml rebinds the shortcuts.
  • actions.toml adds your own SQL to the explorer's and the grid's menus, with names and values quoted for you.
  • snippets.toml adds snippets to completion, with fields to Tab through.
  • theme.toml changes the light and dark themes' colours.
  • exports.toml adds export formats of your own, from templates or programs.
  • Keep them in Git: DbRover keeps your comments and order, and picks up a git pull made while it runs.
  • On a Mac, the menus are in the menu bar, and text takes the system font and accent colour.

It updates itself

DbRover asks GitHub for a newer release when it starts, or from Help › Check for updates…. On macOS and in the AppImage, Install and restart checks the update's signature and puts it in place, and so do Windows copies installed with the installer; the .deb opens the release page instead. The check sends nothing about you, and can be turned off.

Check what you downloaded

Every release has a SHA256SUMS file. In the folder with your download:

shasum -a 256 -c SHA256SUMS --ignore-missing
